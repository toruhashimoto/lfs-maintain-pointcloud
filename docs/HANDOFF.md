## マシン・ビルドを移すときに必ずやること

### 1. どの LichtFeld Studio を使うか記録する

**これまでの結果は同じエンジンで取られていない。** README の RAMESSES/Chest の
A/B（p90 −59% など）は **master のソースビルド**（v0.5.3 より後）で、
2 つ目のデータセットの A/B は **v0.5.1 のプレビルド**で取得した。

`LichtFeld-Studio.exe --version` を最初に記録すること。ビルドが違えば
ノイズフロアも環境の罠も引き継げない。

Windows のプレビルドは **v0.4.2 を最後に GitHub Release から消えた**
（v0.5.0〜v0.5.3 は assets 0 件）。入手は portal.lichtfeld.io（登録が必要）か
ソースビルドの二択。

v0.5.3 は OpenGL/CUDA レンダラを Vulkan に全面置換し、quantized Adam state、
trainer↔render バッファ共有、automatic centralization、Init PLY/Checkpoint 挙動修正を
含む。いずれもこのプラグインの前提（最適化器パラメータメモリへのステップ後書き込み、
初期点群からのアンカー捕捉、means の実効学習率）に触れる。
**検証の途中でエンジンを変えない。**

### 2. VRAM を測り直して `--max-cap` を決める

**`--max-cap` は初期点群の点数以上を明示する。** 下回ると LichtFeld Studio が
警告 1 行を出してランダムに間引き、さらに MRNF が `utilization 100%` で開始して
密度制御が事実上停止する（README「落とし穴」）。

GPU が変われば載る上限も変わる。**前のマシンの前提をそのまま持ち込まない。**
`nvidia-smi` で実容量を確認し、初期点群の点数（COLMAP `points3D.txt` の 3 行目
`# Number of points:`）を上回る値を設定する。参考値: 7,886,332 点・SH 次数 3 で
VRAM 17.1 GB。

### 3. スループットを測り直す

**短縮実行から実行時間を外挿しないこと。** `--steps-scaler` は
`sh_degree_interval` も縮めるため、短尺実行はほぼ全 iteration が SH 次数 3
（係数 48 個）で回り per-iteration が不当に高価になる。実測で 1,500 iter は
3.03 iter/s、30,000 iter は 13.9 iter/s と 4.6 倍違った。さらに 150 iter 程度の
試走で測ると、終了時の checkpoint（数 GB）と PLY 書き出しの固定コストが支配して
無意味な値が出る。**最低 1,000 iter は回してから割る。**

### 4. ノイズフロアを取り直す

MCMC/MRNF はシード固定不可。**必ずベースラインを 2 本回してから効果量と比べる。**
ノイズフロアはマシン・ビルド・データセット・実行長のすべてに依存する。
実測例（hold-out PSNR のアーム内ばらつき）:

| 条件 | ばらつき |
|---|---|
| 44 枚 / master ビルド / 30000 iter | 0.26 dB |
| 1,749 枚 / v0.5.1 / 1500 iter | 0.081 dB |
| 1,749 枚 / v0.5.1 / 30000 iter | 0.051 dB |

## 新しいデータセットで最初に確認する4点

1. **有効になっているか。** `enabled` の既定は False。GUI パネルの `Enabled` か
   `LFS_MPC_ENABLED=1`。判定は統計 JSON の **`applied_iters`。0 なら何も起きていない。**
   過去に一度、これで 2 本とも無効のまま比較して丸一日を無駄にしている。
2. **`--max-cap` が初期点群より大きいか。**（上記「2」）
3. **不感帯が分布の外側になっていないか。** アンカー無効で 1 本回して
   **`init_drift.p95 ÷ config.free_radius_effective`** を計算する。
   **1 を下回っていたら、初期行の 95% 以上が不感帯の内側にいて、リーシュには
   引く対象がない。そのまま A/B を回しても全指標がノイズ以下になる。**
   `free_radius_spacing` を下げてこの比を 1 より大きくしてから比較する。
   実測では比 0.81 で効果ゼロ、`free_radius_spacing` を 1.0 に下げて比 1.61 に
   すると p95 −38%（効果/ノイズ 42）。
4. **テレポート閾値が妥当か。** 起動ログの
   `anchors captured: N rows, scene diag ~X, nn spacing ~Y, free radius Z (auto), teleport thresh T`。
   T は頑健シーン対角（p1–p99）の 1%。自由ドリフトの p95 より小さいと誤検出、
   被写体スケールより大きいと検出漏れ。

## 検証の作法（ここが本体）

n=1 対 n=1 は何も言わない。**各アーム 2 本**が最低条件。実際に、アンカー 1 本だけで
「ドリフト最大の効果/ノイズ 18.3、有意」と読めた数字が、2 本目でアンカー側自身の
ばらつきが判明した途端 **1.0** に落ちた。

`--eval --test-every 8` を付けないと全画像が学習に使われ、PSNR は測れない。

**ベースラインは `free_radius_spacing` を変えても再利用できる。** `enabled=0` では
`_strength_at()` が 0 を返して引き戻しブロックに入らないため、`free_radius` は
モデルの軌跡に影響しない。不感帯の掃引ではアンカー側だけ回せばよい。

### 信用してはいけない指標（すべて実際に誤結論を出した）

| 指標 | なぜ駄目か |
|---|---|
| 学習 loss | hold-out がないと品質を反映しない。構造指標が 0.1% 一致していてもランごとに 22.7% 振れた |
| ドリフトの中央値だけ | 分布が二峰性になる。不感帯の内側にいる大多数は自由に動くので中央値はアンカー無効時とほぼ一致し、作用は上位の裾にしか出ない。必ず p50/p75/p90/p95 と `rows_excluded` を併せて見る |
| ドリフトの最大値 | 単一の外れ行の値で、ベースライン自身が 21.47 対 41.71 と 2 倍振れた。効果 −92% でも効果/ノイズは 1.4 にしかならない |
| 初期点→最近傍スプラット距離（被覆） | アンカーが効いていると「スプラットが自分のアンカーの上に乗っている」ことを測るだけになる |
| 静的なフローター代理指標 | カメラ群から遠い遠景を拾う。フローターを主張するには novel view の描画が要る |
| 短縮実行の結果 | `--steps-scaler 0.05`（1,500 iter）では全指標がノイズ以下だった。PSNR も 18.42（30,000 iter では 27.22）で単にモデルが未収束。**結論には使えない** |

`--steps-scaler` は `warmup_iters` を縮めないので、短縮する場合は
`LFS_MPC_WARMUP` を同じ比率で手動設定する（scaler 0.05 なら 15）。

### プラグイン設置の注意

- **`pyproject.toml` を編集したら `.venv/.deps_installed` を touch し直すこと。**
  プラグインローダは「pyproject の mtime > マーカーの mtime」で依存の再同期を
  試み、**ソースビルドは uv を同梱しないため必ず `uv not found` でロード失敗**
  し、パネルが 1 枚も出なくなる（2026-07-31 に v0.4.0 のバージョンスタンプで

  コピー済み — ただしビルドツリーを作り直したら再コピーが要る。再同期が走ると

  `Set-Content -Encoding utf8` は BOM 付きになり無視される）

## データセット B で分かったこと（結論）

**プラグインは目的を達成しているが、既定の静的不感帯がこのデータセットには広すぎた。**

`free_radius_spacing = 2.0` ではベースライン p95 が不感帯の 0.81 倍、つまり分布全体が
不感帯の内側にあり、全指標がノイズ以下。1.0 に下げて比を 1.61 にすると
p90 −25.6%（効果/ノイズ 25.7）、p95 −38.3%（同 42.3）。着地点は p95 が不感帯の
0.9998 倍、p90 が 0.9965 倍で、**リーシュが不感帯の縁で正確にクランプしている**という
RAMESSES/Chest と同じ signature が再現した。測光コストはどちらの条件でも
検出限界（0.051 dB）以下。

`free_radius_spacing` の既定は変更していない（2.0 のまま）。RAMESSES/Chest では
2.0 で p90 −59% が出ており、1 データセットの結果で既定を動かす根拠にはならない。
**点群密度に対してドリフトが小さいデータセットで下げる**、という運用指針として扱う。
なお `calibrate_quantile` のほうは 2 データセットで一致したので 2026-07-31 に
70 → 60 へ変更した（上記「現在地」）。自己校正を使うならこの静的規則は出番がない。

## 2026-07-29 に決着したもの（記録として残す）

- ~~**ドリフト最大値の決着。**~~ **決着。必要だったのは本数ではなく検定手法だった。**
  「ベースラインを 4 本追加すれば決まる」という当初の見積もりは誤りで、6 本まで
  増やしても効果/ノイズは 1.0 のまま（実測 10.879 / 11.023 / 11.408 / 41.405 /
  79.971 / 93.861、二峰性で 9 倍振れる）。**厳密な並べ替え検定なら決まる**:
  8M cap でアンカー全体(n=4) vs ベースライン(n=6) は **p = 0.0048**、校正のみ
  (n=2) でも p = 0.0357（`scripts/rank_test.py`）。ただし**高 cap では有意に
  ならない**（アンカー側が 1.759 と 16.657 に割れる）。
  なお `max` を使う必要自体が無くなった。同じ裾を `p999` で測ると効果/ノイズ
  199.7、`escaped_2x`（点間隔の 2 倍超の行数）で 100.1 になる。**同じデータ・
  同じ現象で 1.0 と 200 に分かれるので、以後 `max` を効果量として読まないこと。**
- ~~**`free_radius_spacing` の既定。**~~ **座標系が違っていた。** 倍率で見ると
  2 データセットで最適値が割れるが、自由ドリフト分布の分位点で見ると一致する。
  v0.3.0 の自己校正がこれを実行中に測る。
- ~~**q の既定値。**~~ **この時点の判断は「70 のまま」だったが、2026-07-31 に
  60 へ変更した**（2 データセット目で掃引が一致したため。上記「未解決の問い」）。
  ここで分かったのは、対照行が記録した q カーブから、既定の静的規則
  （`spacing=2.0`）が不感帯を **q95** に置いていたこと（＝引く対象が無かった）、
  手動掃引が見つけた最良値が **q70**（比 1.01）だったこと。さらに締めると位置忠実性は
  単調に向上する（p95 −44.9% → −52.4% → −57.9%）が、**代償は測光ではなく
  スプラット形状**（`scale_p90` が +2.1% → +2.9% → +3.4%、いずれも有意）。
  当時「1 データセットの結果で既定は動かさない」としたのはこの形状コストのため。
- ~~**`calibrate_start` の妥当性。**~~ **1000 のままでよい。** 5000 は p50 +6.5%
  （効果/ノイズ 13.1）、p75 +2.5%（6.4）と胴体が悪化し、裾は変わらない。
  早期に強く締めるのは有害ではなく有益だった。
- ~~**対照行のバイアスをどう扱うか。**~~ **機構を特定、補正はしない。**
  強く締めるほど増え（q70/60/50 で +7.69/+8.71/+10.04%）、長く締めるほど増え
  （start=5000 で +4.38%）、自由な行が多いほど減る（対照行 10% で +5.81%、
  高 cap で +4.97%）。**誤差は安全側**（不感帯を広めに選ばせる方向で、締めるほど
  良いのだから緩い側に外れる）。`control_fraction` を上げる対処は**非推奨** —
  対照行は最終モデルで正則化されないので、0.10 にすると置いた点群の 10%
  （789,000 行）が保持されない。バイアス 7.7% → 5.8% の見返りに見合わない。

## 手作業クリーンアップを減らすなら（データセット C・D で確認）

**このプラグインは手作業クリーンアップの主要因を解決しない。** 納品モデルと生成物の
両方が残っていた C で専門家の除去を正解ラベルにして測った結論（2026-07-30）。
**D で再現も取った**（下記）。

除去 76,530 行のうち **74.8% は納品箱の外**（保持側は箱の外 0 行、境界は厳密）。
残り 25.2% は被写体ごとに基準が変わり、一般化できるルールにならない。

| 手 | 箱外スプラット | 箱内 PSNR | 判定 |
|---|---|---|---|
| **入力点群を箱でクロップ** | **−56.0%**（効果/ノイズ 15.5） | −0.24 dB | **これをやる** |
| `nn` + `anchor_new` | −8.6%（3.2） | −0.15 dB | 補助的 |
| `index` + 校正 | −0.3%（0.1） | ±0 | 箱外には無効 |
| 学習中クロップ箱 | −26.1%（9.6） | **−3.71 dB** | **やってはいけない** |

**入力点群のクロップが唯一の実用的な手。** `points3D.txt` を箱でフィルタするだけ
（4.3M 点で 7 秒）。撮影点 4,302,501 のうち 29,175 点（0.68%）が既に箱の外にあり、
学習はそこにスプラットを育てていた。**アンカーはむしろその点の上に行を留める**ので
`index` は効果ゼロ。余白は 5% 取る（納品後の箱は事前に知り得ないため）。

**学習中クロップ箱（`LFS_MPC_CROP_BOX`）は実装したが使ってはいけない。**
箱外は 26% 減るが**納品する領域そのものが 3.71 dB 悪化する**。全画面 PSNR だけを
見ると「背景を捨てたのだから当然」と誤読する。`scripts/inbox_psnr.py` で箱の内側
だけを測って初めて分かった。**領域を絞って学習するなら、全画面 PSNR は納品物の
品質を測れない。**

`nn` + `anchor_new` を使う場合、追加行は次の retarget まで未アンカーで開始すること
（`anchor_policy.py`）。しないと `nn_refresh` iter のあいだ誕生位置に引かれ、
v0.1.0 の失敗を小口で連続再現する。

### 2 つ目の被写体（D）で再現した（2026-07-30, 30,000 iter × 8, ラベル = 納品モデル）

| 比較 | 効果 | 効果/ノイズ |
|---|---|---|
| **クロップで箱外スプラット** | **−59.1%**（C の −56.0% の再現） | **51.1** |
| クロップの箱内 PSNR | **+0.11 dB**（コストなし。C は −0.24） | 3.7 |
| 未クロップ + `nn` の箱外 | −2.4% | 4.3 |
| クロップ済み + `nn` の箱外追加 | −4.2% | 1.3 = **結論未満** |
| クロップ済み + `nn` の箱内 PSNR | **−0.29 dB**（C の −1.04 と方向一致） | 2.0 |

**運用の結論: クロップのみを既定にする。** `nn` を重ねるのは撮影面への忠実性
（箱内 p99 距離 3.6 → 1.0 点間隔）が目的の場合だけ。

run ディレクトリが残っているマシンなら、いつでも再集計できる:

### 公称箱の座標（2 データセットの納品モデルで確定）

COLMAP フレームで **`-1,-1.5,-1:3,0.5,1`**（中心 `[1,-0.5,0]`・サイズ `[4,2,2]`）。
クロップにはこれを `--box` に渡す。

以前の記録「中心 `[-1,0.5,0]`」は **x, y の符号が逆**で、そのまま当てると D の
点群の 27.1% が落ちて被写体が箱に入らない（符号を直すと 7.7%）。符号反転が正しい
ことは 2 データセットの納品モデルの実測箱で確認済み — 公称箱はどちらの実測箱も
内包する:

| | C | D |
|---|---|---|
| 実測箱 lo | `-0.8777, -1.2579, -1.0000` | `-0.9992, -1.4594, -1.0000` |
| 実測箱 hi | `3.1204, 0.3682, 1.0000` | `2.1650, 0.3634, 0.9999` |
| 公称箱との lo 差 | `0.122, 0.242, 0.000` | `0.001, 0.041, 0.000` |
| 公称箱との hi 差 | `-0.120, 0.132, 0.000` | `0.835, 0.137, 0.000` |

z の差は 4 面中 3 面で 0.000、残る 1 面も 0.0001 — 納品時の z 制限は実質ちょうど
±1 で、公称箱は実在する規約であっておおよその目安ではない。ただし **C は hi 側で
公称箱を 0.120 超える**ので、余白 5%（`--pad` 既定）はそのまま必要。

**評価に使う箱と、クロップに使う箱を混同しないこと。** クロップには公称箱を使う。
そのデータセットの納品モデルから測った箱でクロップすると、正解ラベルを入力に
混ぜたことになり効果が過大に出る（本番では納品箱はまだ存在しない）。

### 箱内除去の予備解析（2 データセットのラベル）

- 特徴の**序列**はデータセット間で一致する（箱境界への近さ `face`、撮影点の局所密度
  `dens8` がトップ 2）。**絶対閾値は移転しない**
- **分位点ルール**（`face` + `dens8` の上位 5%、ラベル不要）が箱内除去の
  **51.1% / 53.2%** を捕捉する。精度は基底率なり（4.0% / 19.4%）なので
  **自動削除ではなくレビュー絞り込みに使う**。n=2 データセットの予備結論
- 特徴キャッシュは各 `colmap/output/_inbox_features_*.npz`（`inbox_rule.py` が自動再利用）
